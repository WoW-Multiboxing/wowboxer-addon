# CLAUDE.md – wowboxer-addon (WoWBoxer in-game addon, workstream E)

## Goal
An all-round multiboxing addon with the **companion at its core**, inside the game. Set up your squad (characters,
class, role, leader/follower). Per character and level it gives you what the web companion gives: recommended
talents/guide, macros and sequence keys for your level. It creates those macros (out of combat, after a click), places
them on your action bars and, on level-up, offers to update them (same names and keys, new bodies). Plus multibox
helpers: leader/follow/assist checklist, recommended CVars (allow-list, backup + restore), recommended addons check,
and import/export of setups as a string shared with the website/companion.

- Name **WoWBoxer**. Slash `/wbx` and `/wowboxer`. Macro names start with `WBX` – never touch any other macro.
- Clients: **Forever** (launch 4 Nov 2026, modern API, `## Interface: 16001`, game type `camelot`) and **Classic Era**
  (1.15.x, 11509). One package, capability probes in `Compat.lua`, never project IDs alone.
- Plan and decisions: `02_Spec/Addon-plan.md` in the project folder
  `<project folder>` (internal docs in Danish); `LOG.md`
  blocks tagged `[WS-E]`. Research: `01_Research/platform/04-addon.md`. Companion: `02_Spec/Handover-v8.md`.
- **Owner:** one session at a time. Since 2026-10-27 the local Claude Code session on the owner's PC owns workstream E
  (it is the only one that can install into WoW and read SavedVariables). Fetch before every push.

## Hard rules (non-negotiable)
1. **No input broadcasting**: nothing outside WoW sends keys or clicks to the game. Every cast, target, move,
   follow and NPC interaction comes from the player's own key press on that character (one press = one action),
   and the addon never tries to get around protected actions or hardware-event checks. **Addon automation through
   WoW's normal API is allowed** (accept, share, sync, sell, repair, loot, trade) as a named option in Setup →
   Automation with a short line about what it does, and it only reacts to **squad members** (the WoWBoxer squad,
   matched by name, in the party). (the owner, 29 Oct 2026; `docs/automation-policy.md`)
2. Imported data is data only: never `loadstring`/`RunScript`/`load` on anything from outside.
3. Macros ≤ 255 chars, names ≤ 16 chars with the `WBX` prefix, slash-command whitelist (reject `/run /script
   /console /click`). The addon builds macro bodies itself; share strings carry no macro text.
4. Every write (macros, action bars, CVars, bindings) happens only after a player click/command and only out of combat
   (`Core.whenSafe` queues it until `PLAYER_REGEN_ENABLED`).
5. Cross-client addon messages may trigger the automations in rule 1, but only from squad members in the party, and
   each one only when its option is on. Messages are data only (rule 2).
6. Same macro rules per squad role as the companion. Data licences: Zephras CC BY 4.0 credit; Blizzard owns
   names/icons/texts. Free, no ads, no in-game donation requests, never obfuscated (UI Add-On Policy).
7. Forever facts get re-verified on the launch client; unknowns are marked `[AFKLAR: …]`, never guessed.
`tools/lint51.py` enforces Lua 5.1 syntax and the forbidden-API list.

## Source of truth: the companion
- `vendor/companion/` is a read-only snapshot of the web companion (data + macro rules).
- `WoWBoxer/Data/*.lua` is generated by `tools/build_data.js` – never edit it by hand.
- `Engine.lua`/`Kit.lua` are ports; `tests/parity.lua` must stay at 0 failures (vectors: `node tools/export_vectors.js`).
  Changing macro behaviour means changing the companion first (workstream A), then re-syncing.
